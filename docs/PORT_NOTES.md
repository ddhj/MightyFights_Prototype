### T0.4 — Mercury API surface

Grep-verified against plan §4/§3. **17 files reference `ProjectMercury`**, matching plan §1
exactly. The actual surface is broader than plan §3's sketch — corrections below should be
folded into Phase 3 (T3.1/T3.2) and Phase 4 (T4.2) scope.

**Correction 1 — `ParticleEffectManager` is a real, directly-used class, not just implied by naming.**
Plan §3 doesn't mention it at all. Game code subclasses it
(`TerminatingParticleEffectManager : ParticleEffectManager`, `Support Classes/Particle System Objects.cs:56`)
and calls, directly on instances:
- `new ParticleEffectManager(Renderer)` — constructor
- `.Add(ParticleEffect)`
- `.Update(float elapsedSeconds, bool)` — **2-arg overload**; second bool parameter's semantics
  are unconfirmed (called as `base.Update((float)cTime.ElapsedGameTime.TotalSeconds, false)`
  in `TerminatingParticleEffectManager.Update`). Needs a Mercury source/decompile check before
  the shim signature is locked in T3.2 — don't guess the parameter's meaning.
- `.Count` (property)
- `.Draw()` — **parameterless**. No `SpriteBatch` or `Matrix` is ever passed by caller code
  (see `BObjectManager.cs:161-166`, `CObjectManager.cs` equivalent) — the manager/renderer owns
  its own draw state internally.
- `.Clear()`
- Enumerable as `IEnumerable<ParticleEffect>` (`foreach (ParticleEffect cEffect in _cParticleSystemMgr)`)
- Indexer + implicit list removal (`this[iCount]`, `this.RemoveAt(iCount--)` in
  `TerminatingParticleEffectManager.Update`) — i.e. it behaves like `List<ParticleEffect>`.

**Correction 2 — `RenderEffect` is never called directly from game code.**
Plan §3 assumed `SpriteBatchRenderer.RenderEffect(ParticleEffect, ref Matrix)` is a call site
to verify. Grepped the full game project — zero direct call sites. Only
`ParticleEffectManager.Draw()` is called; it must internally iterate its effects and invoke the
renderer. This means the shim only needs `ParticleEffectManager.Draw()` to behave correctly
end-to-end — there's no external contract on `RenderEffect`'s exact signature to match.

**Correction 3 — `ParticleEffect.Terminate()` is called and not in plan §3.**
Two call sites: `BObjectManager.cs:179`, `CObjectManager.cs:149` (both inside a
`Clear()`-adjacent path, iterating `_cParticleSystemMgr` and calling `.Terminate()` on each
effect before the manager itself is cleared). Add to shim's `ParticleEffect` surface.

**Confirmed (matches or refines plan §3):**
- `ParticleEffect` behaves as a `List<Emitter>` subclass: `TerminatingParticleEffect`'s
  constructor (`Particle System Objects.cs:25-33`) does `this.AddRange(cEffect)` and copies
  `Author`, `Capacity`, `Controllers`, `Description`, `Name` — all plain get/set properties,
  copied but never branched on in gameplay code, so the shim can implement them as inert
  metadata fields.
- `ParticleEffect.Initialise()`, `.Update(float)`, `.LoadContent(ContentManager)`,
  `.Trigger(Vector2)`, `.DeepCopy()` — all confirmed used exactly as plan §3 described.
- `Emitter.Term` (float) and `Emitter.ParticleTextureAssetName` (string, mutated at runtime —
  `DataManager.cs:263-264` and `:282-283` prefix it with `Particles\` before load) are the only
  `Emitter` members touched from C#. Everything else emitter-side (Budget, ReleaseSpeed, etc.)
  is XML-only tuning data, never read/written from game code — safe to model as data-only in
  the shim, no runtime mutation contract beyond `ParticleTextureAssetName`.
- `Renderer cRenderer = new SpriteBatchRenderer()` — field is typed to the **base** `Renderer`
  class, confirming `SpriteBatchRenderer : Renderer`. `.GraphicsDeviceService` (settable) and
  `.LoadContent(ContentManager)` confirmed as plan described.

**Particle XML inventory (all 15 files, 35 emitters total) — refines plan §3/T4.2:**

Emitter types actually used:
| Type | Count |
|---|---|
| LineEmitter | 5 |
| RectEmitter | 5 |
| ConeEmitter | 2 |
| CircleEmitter | 1 |

Plan §3 guessed "CircleEmitter, PointEmitter, maybe ConeEmitter." **No `PointEmitter` is used
anywhere.** `LineEmitter` and `RectEmitter` — unguessed by the plan — are actually the two most
common types. T4.2 should target CircleEmitter/ConeEmitter/LineEmitter/RectEmitter, not PointEmitter.

Modifier types actually used (32 `<Modifiers>` blocks):
`ColourModifier` (2), `DampingModifier` (1), `HueShiftModifier` (1), `LinearGravityModifier` (5),
`OpacityFastFadeModifier` (1), `OpacityInterpolatorModifier` (9), `OpacityOscillator` (1),
`RotationModifier` (4), `ScaleInterpolatorModifier` (1), `ScaleMergeModifier` (1),
`ScaleModifier` (3), `TrajectoryRotationModifier` (2) — **12 distinct modifier types**, richer
than plan §3's guess of "opacity/scale/colour interpolators, gravity/damping if present."
Add `HueShiftModifier`, `OpacityOscillator`, `TrajectoryRotationModifier`, `ScaleMergeModifier`,
`OpacityFastFadeModifier`, `DampingModifier` explicitly to the T4.2 implementation checklist —
none of these are obviously guessable from the plan's hedge language.
